# @moguiyu/dsh-tavily 0.8.0 与 DSH 0.2.2-rc.2 的兼容性核对

- 目标版本：DSH `0.2.2-rc.2`，tag `dsh-v0.2.2-rc.2`，commit `ddac96760b6edf8fa0fe17cbdcf0b512f4c12b2c`
- 本机安装：DSH `0.2.2-rc.1`，Node `v24.22.1`；本次不升级本机安装
- 核对日期：2026-11-11（Asia/Hong_Kong）
- 结论：接口契约兼容，未发现阻断性不兼容。rc.2 对本插件的改动集中在未使用的路径与外部约束上，插件代码无需修改。

## 1 版本状态

rc.2 相对 rc.1 是一次语义发布：全仓 4645 个文件变化，其中本插件直接依赖或受其约束的 11 个包占 85 个文件。变化的主体是 Team 模式进入 base、MCP 管理器、Office kit、账号服务合并、Web 搜索 provider 选择器，以及工具管线的结构化错误身份。

有一项发布事实需要先记录：核对当天，npm 上 `@deepseek-ai/dsh` 的 `latest` 与 `next` 仍是 `0.2.2-rc.1`，`@deepseek-ai/dsh@0.2.2-rc.2` 与 `@deepseek-ai/dsh-tools@0.2.2-rc.2` 都返回 404，而已发布的 `0.2.2-rc.1`、`0.2.1-rc.5` 可以正常解析。rc.2 目前只以 Git tag 的形式存在，无法从 npm 安装，因此本轮核对是源码级，不是安装级。

## 2 兼容门禁与版本声明

门禁函数 `evaluatePluginCompatibility`（`packages/boot/app-boot/src/plugin-compatibility.ts:87`）在 rc.1 与 rc.2 之间没有任何差异，`git diff` 为空。以 rc.2 的版本号求值本包的 `package.json`，返回 `undefined`，即 compatible；以 `0.3.0` 求值被拒绝，并列出 `@deepseek-ai/dsh-home-paths` 与 `@deepseek-ai/dsh-tools` 两项未满足要求。

peer 范围在两种模式下的匹配结果一致：`^0.2.2-0` 在默认 semver 规则与 `includePrerelease: true` 下都接受 `0.2.2-rc.2`；`@deepseek-ai/cordis` 的 `^4.0.1 || ^4.0.6-alpha.2` 接受 `4.1.0`，而 cordis 从 rc.1 起就是 `4.1.0`，本轮未变。

需要修正一处认识：`package.json` 里的 `dsh.compatibility.dshReleases` 在 rc.2 源码中没有任何读取点。对整个 tag 执行 `git grep dshReleases` 没有结果，门禁只依据 `engines.dsh`（存在时独占判断）或 `@deepseek-ai/dsh*` 的 peer 范围。该字段目前是文档性声明，往其中补一条 `"0.2.2-rc.2": "compatible"` 不会改变任何判定结果，只是让清单与实测记录对齐。

## 4 rc.2 引入的行为变化

这些变化不构成不兼容，但会改变运行时的可观测行为，升级后值得留意。

凭据服务的 `describe` 现在可以返回提供方生成的掩码预览。本插件用自己的 `maskValue` 计算掩码并以掩码值作为管理接口的标识，不读取 `masked`，因此密钥列表、排序与揭示接口的行为不变。

工具管线新增了结构化错误身份：守卫可以返回带 `info` 的拒绝对象，审批拒绝统一记录为 `ApprovalError` 加 `APPROVAL_REJECTED` / `APPROVAL_CANCELLED` / `APPROVAL_UNAVAILABLE`，新增 `ToolContextUnavailableError`。本插件的四个工具在失败时抛出普通 `Error`，模型可见文本与 rc.1 相同，只是结果里没有 `info` 字段。另有一处细化：取消后若抛出的是信号原因或未分类的 `AbortError`，结果会带上 `ABORTED` 身份（`pipeline.ts:286`）；插件在 `exec.signal` 触发后放弃的 `fetch` 会走这条路径，属于信息更完整而非行为改变。

PTC 执行器新增每分钟子调用额度 `maxSubCallsPerMinute`，默认 1024，按 `run_code` 的解析超时折算（`ptc.ts:698`），失败调用也计入；同时新增程序环境 reset。四个 Tavily 工具在 PTC 预设下作为 SDK 绑定出现，单次 `run_code` 内对它们的调用次数受该额度约束。常规用法远低于默认值，长循环内的批量 crawl 才可能触及。

客户端条目加载的容错有变化：某一条目创建失败时只记录日志并保持为 inactive，不再中断启动（`packages/client/modules/src/client/entries.ts:97`）。卡片 bundle 若构建损坏，现在表现为「插件列表里没有卡片」，而不是整个界面启动失败，排查时不能只看启动是否成功。

Web 子系统重排：`web-search-exa` 与 `web-search-perplexity` 两个包被删除，base 的默认搜索 provider 从 `deepseek-official` 改为 `deepseek-search-api`，并在设置页提供 provider 选择器。本插件不注册 provider、不触碰 `ctx.web`，内置 `web_search` 与 `web_fetch` 由这些行提供，与本插件并行存在。README 中「0.2.2 把工具呈现移出 dsh-tools、`mode` 与 `maxParallelSubCalls` 被拒绝」的说法在 rc.2 仍然成立（`packages/core/tools/src/index.ts:103` 仍是 `z.never()`）。

客户端槽位服务新增 `hoc` 种类，属于附加能力，keyed 槽位的注册、影子与渲染规则未变。渲染器差异只有注释。

## 5 实际执行的检查

`npm run check` 通过，七个源文件语法检查无误。

`npm test` 在当前依赖（DSH 0.2.2-rc.1 的 `@deepseek-ai/dsh-tools` 与 `dsh-home-paths`）下 69 项全部通过。这一轮没有重复 0.2.2-alpha.3 核对时的 loader hook 替换，理由是 rc.2 的 `json-schema.ts` 与 `schema.ts` 与 rc.1 无差异，而 `index.ts` 的改动只涉及守卫与错误身份，插件未使用；但这也意味着测试仍然跑在 rc.1 的代码上。

以 rc.2 的版本号调用门禁函数，得到 compatible；以 `0.3.0` 调用得到拒绝。

用 semver 对 peer 范围做了两种模式的矩阵验证，`0.2.2-rc.2` 与 `4.1.0` 都满足。

源码级核对覆盖了 rc.1 到 rc.2 在 `packages/core/tools`、`packages/core/system-prompt`、`packages/credentials/credentials`、`packages/util/home-paths`、`packages/host/webserver`、`packages/client/modules`、`packages/client/ui-slots`、`packages/client/ui-plugin-manager`、`packages/boot/plugin-manager`、`packages/boot/app-boot`、`packages/bundle/base`、`packages/bundle/web-app` 的全部改动。

## 6 未覆盖

没有启动真实的 DSH 0.2.2-rc.2 实例，因此未验证真实组合下的行激活、浏览器卡片渲染与交互、PTC 模式下的 SDK 调用、真实 Tavily 请求、HMR 与远程访问。第 3 节的核对依据是源码与已安装包的符号对照，不能代替真实 Cordis 组合。

由于 rc.2 尚未发布到 npm，安装、升级、卸载这条链路完全没有验证。等 rc.2 发布后应补一次真实安装冒烟：安装本包、确认两条路由登记、打开卡片、发一次 `tavily_search`。

## 7 后续可选的整理

`package.json` 的 `dshReleases` 与门禁的实际判定脱钩，若继续保留该字段，宜在 README 中说明它只是发布记录，避免读者误以为它能放行版本。是否补 `0.2.2-rc.2` 条目属于记录习惯，不影响兼容性。

两段提示的 `order` 取 111 与 112，落在 `DEPLOYMENT_PERSONA_PREFIX`（0）与 `PLAN_POLICY`（500）之间，因此排在内置的计划段与全部 `TOOL_*` 段之前，而不是紧邻 `TOOL_WEB_SEARCH`（2000）。这一行为在 rc.1 与 rc.2 中相同，不属于本轮兼容问题，但会影响模型看到的段落顺序。
